# Inactive Tool binding catalog and dispatcher

Status: test-only implementation; no live binding or production activation approved.

The server-owned catalog maps an exact agent ID/version, domain, intent and conceptual capability to one concrete Tool ID/version and input/output schema IDs. It rejects duplicate scopes, ambiguous binding revisions, stale registrations, wildcard capabilities, proposals and live registrations. Descriptors are copied and frozen. Its default contents are empty; inactive entries and disabled registrations cannot execute or validate bound evidence. Registration schema IDs identify the exact registered schemas; this increment introduces no schema negotiation or latest-version resolution.

The inactive dispatcher implements the existing Gateway structured `tools` adapter boundary. Its initial scope is a single `asset.get` candidate for `ASSET_LOOKUP`, read/low risk, with an exact Asset ID input/output projection. It captures immutable arguments and the entire trusted context before awaiting routing. A per-invocation grounding closure checks every captured context field, correlation, agent, version, intent and conceptual capability before calling Tool Runtime. No serialized prepared packet or caller-supplied binding is accepted. The normal Gateway, routing, Pilot and Tool Runtime authorization, feature, registration, ownership, rate and audit checks remain in place.

Pilot's optional trusted catalog resolves conceptual capabilities when validating Tool evidence. Concrete responses and citation IDs/versions remain unchanged. Without the option, its existing concrete-ID evidence behavior is retained. Neither a mapping nor the test option approves an intent or enables a production profile. Only explicitly composed deterministic tests can execute this slice; the dispatcher rejects every non-test environment and has no application/bootstrap composition.

This is additive implementation under baseline 05 Tool API contract §§58–59 (Platform mapping/orchestration, Core business authorization), technical design 16 §§7–8, 17–19 (shared routing and conceptual-to-concrete mapping), and implementation plan 17 Phase 3/5. It changes no baseline, public wire field, production profile, Core authorization or network/security policy. Core proposals remain PROPOSED with D01–D09 OPEN. Release remains blocked pending separately approved production binding and evidence.

Focused tests cover the real Gateway/routing/Pilot/Tool Runtime chain, exact catalog contracts, inactive defaults, disabled/blocked/denied execution, forged bindings and evidence, route broadening, full captured context, concurrent immutable arguments and legacy compatibility. Existing synthetic Core, tenant/security and legacy component tests remain applicable. No dependencies, credentials or real Core transport are introduced.
