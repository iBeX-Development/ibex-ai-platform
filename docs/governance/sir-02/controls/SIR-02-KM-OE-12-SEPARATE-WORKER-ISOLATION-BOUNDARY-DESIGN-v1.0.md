## 2. Normative disposal object: two bounded obligations

The active [OE-12 Criterion Amendment v1.1](SIR-02-KM-OE-12-CRITERION-AMENDMENT-v1.1.md), [Acceptance Matrix Amendment v1.1](SIR-02-KM-OPERATIONAL-EVIDENCE-ACCEPTANCE-MATRIX-AMENDMENT-v1.1.md), [Execution Plan Amendment v1.1](SIR-02-KM-OPERATIONAL-EVIDENCE-EXECUTION-PLAN-AMENDMENT-v1.1.md), and [Authoritative Validation-Boundary Detailed Design v1.0](SIR-02-KM-OE-12-AUTHORITATIVE-VALIDATION-BOUNDARY-DETAILED-DESIGN-v1.0.md) require the following **combination**, not a choice among weaker substitutes:

1. **Authoritative validation boundary:** for each unique run/generation, the controller must reach one immutable terminal decision within an approved finite bound, atomically fix an Accepted Result Cutoff, revoke acceptance of later results, and prove that the authoritative outcome cannot change after closure.
2. **Owned worker/isolation boundary and resources:** the execution worker or session, together with the process instance if a process is selected, its owned query/session objects, channels, handles, subscriptions, and temporary resources, must have a **proven finite lifetime and deterministic, ownership-aware, non-destructive disposal**. An unresponsive CIM operation is an applicable failure case. Closing the result gate, timing out, releasing a controller handle, or recording `Disposal Unresolved` is not proof that this second obligation passed.

The shared CIM provider's **physical termination or complete internal quiescence is not the disposal object demanded by the active replacement criterion**. Its outstanding-operation state and any late effects must still be observed and fenced from the authoritative outcome; physical provider quiescence must not be asserted without direct proof. If a later concrete topology places an owned provider operation or session inside the worker boundary, its ownership and disposal state must be accounted for as an owned resource. The bounded worker obligation cannot be silently reduced to collector stability or result fencing.

This interpretation follows the criterion's separate clauses for bounded terminal closure and proven finite worker/isolation lifetime, the Matrix's requirement to measure closure, isolation lifetime, and disposal separately, and the published worker design's explicit **`Design GAP — Separate Isolation Boundary Required`** finding. The normative object is sufficiently specified for a design assessment; no weaker interpretation is inferred.

## 3. Conceptual architecture and authority limits

The required logical flow is:

`Authoritative Controller → Run / Generation Authority → Isolated Worker Boundary → Read-Only CIM Operation → Result Channel → Late-Result Fence → Immutable Authoritative State → Independent Audit Evidence`

An independent GAP-A receipt producer and integrity anchor must supply trusted ownership evidence to the controller and identity checks. It is an external mandatory dependency, not a capability supplied by the worker or this proposal. Logical separation does not select a process, session, transport, storage engine, or OS primitive.

**Worker lifecycle state and authoritative validation terminal state are separate state domains and MUST NOT be used interchangeably.** A worker lifecycle outcome does not itself set or mutate the authoritative terminal state. Only the Authoritative Controller may transition the validation boundary to exactly one authoritative terminal value — `Success`, `Timeout`, `Fail`, or `Cancelled` — under the governed acceptance rules. The worker/provider supplies candidate observations only; `WorkerCompleted` does not automatically mean authoritative `Success`.

| --- | --- | --- | --- |

No worker, CIM provider, result channel, or fallback may directly mutate terminal state, Accepted Result Cutoff, ownership record, or independent audit decision. Tenant/source isolation, authorization, tenant-safe denial, sanitized metadata, and the OE-08 synthetic audit-only boundary remain mandatory.

## 4. Isolation mechanism selection gate

Assessment is against the current host and retained evidence, not an execution experiment. Every class would need finite worker/resource disposal **including a stalled CIM path**, independent identity, fresh full ownership proof, no unknown-process impact, bounded cleanup authority, run/generation fencing, independent audit, and no unapproved elevation, configuration, dependency, or runtime changes.

| Isolation class | Result fencing and run binding | Finite disposal / ownership / child behavior | Host, authority, and decision |
| --- | --- | --- | --- |
| Same process, thread, or PowerShell runspace | A separate logical result gate could fence late output. | Retained exact-source safety review `76e20519b3395faf012c6231d818eaf9e8532690` found `BeginStop`, timeout waits, and disposal do not prove bounded completion of a hung pipeline. No independent process identity or finite disposal of unresponsive in-process work is established. | **Fails mandatory finite-disposal gate**; no compliant preference. |
| Separate worker process | Controller-owned fence could reject stale/post-cutoff output and bind a unique generation. | Process exit could be observed with a retained handle, but cooperative cancellation/natural exit cannot guarantee a bound for a hung worker. A process-affecting disposal method and independently authenticated parent/child/helper identity are not approved or proven. A merely abandoned live worker fails the finite-lifetime requirement. | No current source, accepted ownership anchor, non-destructive disposal mechanism, or direct timing proof. **Candidate only; not compliant under current boundary.** |
| Retained handle and CIM session/operation boundary | Handles may support identity observation and controller-owned channel disposal. | Handle or session closure alone does not prove the underlying worker/operation exited within a finite bound; prior in-process review left stalled work unresolved. Retained handle identity also does not replace an independent creation/assignment receipt. | **Observability aid, not a sufficient isolation/disposal boundary.** Exact API lifecycle and host compatibility require later governed proof. |
| Windows Job Object or equivalent OS process group | A separate result gate could still fence accepted output. | Failed Smoke v4 forensic record retained an **unknown Job member** and a Job-wide destructive fallback; membership alone did not authenticate ownership. Kill-on-close or Job-wide termination can affect every member, so neither is a safe default. Descendant/conhost identity and complete membership are unproven. | Job creation/assignment of one intended parent was observed, but safe bounded group disposal was **not**. No Job-wide action, unknown-member termination, or fallback is selected. |
| Container or fully isolated provider/OS boundary | Might isolate result authority if independently governed. | Complete worker/provider membership, finite cleanup, privilege and environment effects, and ownership are not established for this host. | Requires separate feasibility/change control if it entails elevation, OS/CIM configuration, dependency, or production impact. **Not currently compliant or selected.** |

**Design STOP — No Compliant Isolation Boundary Identified.** A separate worker process is a useful *conceptual* isolation class for a later governed study, but no class above currently satisfies all mandatory disposal, ownership, unknown-member safety, and host compatibility controls. No preferred implementation is selected. No destructive or wider-authority fallback is supplied. This STOP does not assert that Windows Job Objects or every possible future isolation method is broken; it records the present evidence and approval limit.

## 5. Ownership gate and worker state machine

Before any process/resource-identity-affecting disposal action, the independent authority must freshly revalidate **`PID + image path + parent PID + creation time + run token + creation/assignment evidence`** against the pre-probe, probe-independent GAP-A receipt, with retained handle/session/Job identity and **all actual members** where applicable. Check the current process instance, role, run/generation, and membership immediately before the action; a prior PID list or earlier match is insufficient. Independent producer identity, pre-probe sealing, integrity anchor, PID-reuse resistance, and Node/conhost provenance remain **GAP-A = OPEN / mandatory**.

`Ownership evidence valid → a separately approved process-affecting action may be considered.` It is not automatically authorized. `Missing, stale, conflicting, reused PID, image/parent/creation-time/token mismatch, unexpected member, or probe-only receipt → STOP — Ownership Revalidation Failed`. Fail closed without PID-only action, unknown-member action, or fallback bypass. If the only way to obtain full proof is new trust-boundary implementation or runtime evidence, stop for separate change control.

The **worker/resource lifecycle** contract is:

`Created → Ownership Bound → Ready → Running → WorkerCompleted | WorkerTimedOut | WorkerFaulted | WorkerCancellationObserved | WorkerUnresponsive → DisposalPending → Disposed | DisposalFailed / Isolated`

`Ownership Bound` requires GAP-A proof; `Ready` requires reviewed source and exact run/generation binding. `WorkerTimedOut`, `WorkerCancellationObserved`, and `WorkerUnresponsive` are worker/resource observations, **not** evidence of worker exit or disposal. `DisposalFailed / Isolated` retains unresolved resources and does not claim that the worker was safely disposed. Separately, the **authoritative validation boundary** follows `Prepared → Open → Closing → exactly one Success | Timeout | Fail | Cancelled`; `Acceptance Closed` is the controller-recorded boundary event, not a worker state or proof of disposal. Only the Authoritative Controller may make that transition under the governed acceptance rules; no worker outcome automatically maps to a terminal value. Once terminal, authoritative state cannot return to active, the Accepted Result Cutoff cannot advance, the generation cannot be reused, and worker lifecycle changes or late/stale deliveries cannot modify the accepted result set or terminal reason. Any retry requires a separately governed new run/generation.

## 6. Bounded closure and disposal protocol — conditional contract

The later approved design must assign and retain positive finite bounds **`T_close`**, **`T_grace`**, **`T_dispose`**, and **`T_total`** before execution, measured with a monotonic clock and UTC evidence. `T_close` bounds the authoritative terminal decision. `T_grace` bounds cooperative cancellation/observation. `T_dispose` bounds the approved physical worker/resource disposal action and verification. `T_total` must cover the applicable staged worst case, including cleanup and independent evidence sealing; a watchdog may detect a missed bound but may not silently enlarge disposal authority. This proposal assigns no numerical durations and claims no bound has been proven.

1. Stop new admission and atomically close authoritative acceptance within `T_close` with one terminal state, reason, timestamp, accepted count, state reference, and explicit immutable **Accepted Result Cutoff**.
2. Revoke that run/generation's result authority. Route every later or stale delivery only to `Late / Rejected` non-authoritative audit metadata; the worker cannot reopen acceptance.
3. Request approved cooperative cancellation where supported; record the request, acknowledgement or absence, operation/session state, and bounded `T_grace` observation.
4. If natural/cooperative exit is independently verified, freshly check resource identity, then dispose only owned handles, sessions, subscriptions, channels, and temporary files in a specified order within `T_dispose`; record each result.
5. If exit is not verified, **do not infer disposal from timeout, result fencing, cancellation, or handle release**. A process-affecting action could be considered only after a separate reviewed design, owner approval, implementation change control, full fresh ownership and membership proof, exact-source safety review, and execution authorization. No such action is selected here.
6. At each bound, record the actual outcome. On an unresponsive worker without an authorized safe mechanism, close the authoritative result, record `Disposal Failed / Isolated` and **fail the worker-disposal acceptance gate**. Preserve unresolved operation/member/handle state and independent audit evidence. Do not relabel as `Disposed` or claim GAP-B closure.
7. Seal independent closure, rejection, disposal, cleanup, and source-integrity evidence. Independently compare final authoritative state against closure state; retain any audit-sink/partial-write failure as a separate failure.

Thus the protocol is **finite for decision and observation**, but it is **not yet a finite successful disposal protocol for a stalled worker**. That is the precise Design STOP. A later process-affecting or different isolation mechanism must undergo separate governance; availability of termination APIs alone does not make destructive action acceptable.

## 7. Late-result safety and failure paths

Future retained closure evidence must include run ID, generation ID, trusted synthetic context, closure timestamp, terminal state/reason, immutable Accepted Result Cutoff, accepted count, closure authoritative state version/hash, late/stale count and rejection dispositions, final state version/hash, and **accepted post-closure mutation count `0`**. The invariant is **`authoritative_state_after_closure == authoritative_state_at_closure`**, except separately labeled non-authoritative rejection/audit metadata. No late provider activity may alter the terminal reason, accepted results, ownership state, or authoritative audit decision.

The table describes future conceptual behavior. Worker outcomes in these rows are observations only. For each path the Authoritative Controller must separately select **exactly one** of `Success`, `Timeout`, `Fail`, or `Cancelled` under the applicable governed validation rule; no worker status automatically determines it. Before any execution, each applicable path must be mapped to actual independently reviewed executable source as **`trigger → exact reviewed source → branch/function → exact API/call → state transition → ownership check → cleanup/disposal → retained evidence`**. Each path must say `Ownership Check = Required` or `Ownership Check = Not Applicable — <reason>`; process/resource actions require fresh full-identity checks immediately beforehand. Prose cannot satisfy that source gate.

| Trigger | Conceptual closure, safety, disposal, and evidence obligation |
| --- | --- |
| Normal completion | Record `WorkerCompleted` only when worker completion is observed. Accept only complete pre-cutoff observations; the Controller closes the validation boundary as `Success` only if all governed acceptance rules pass, otherwise selects the applicable authorized terminal state. Verify actual worker exit, owned-resource disposal and independent audit before claiming evidence success. |
| Inner timeout / outer watchdog timeout | Record `WorkerTimedOut` or `WorkerUnresponsive` as observed, without treating either as exit. The Controller closes the validation boundary under the governed timeout rule as `Timeout` within `T_close`; record both timing stages, outstanding query and worker states, cooperative request, bounded wait and distinct disposal outcome. Watchdog observes/signals/records only. |
| Cancellation | Record `WorkerCancellationObserved` only when observed; the Controller closes the validation boundary as `Cancelled` when the governed cancellation rule applies. Record request/acknowledgement, later response disposition, bounded wait and cleanup. Cancellation request is not disposal proof. |
| Worker exception / launcher or child early exit | Record `WorkerFaulted` where the worker fault is established, or the distinct early-exit observation. The Controller closes the validation boundary as `Fail` when the governed failure rule applies; sanitize error, preserve partial lifecycle and handle state, and verify exit and cleanup independently. |
| CIM provider exception or service failure | Record the provider failure separately from the worker state. The Controller closes the validation boundary as `Fail` when the governed failure rule applies; retain sanitized native/provider category and operation/session state. Do not infer provider or worker quiescence. |
| Partial or missing result | Reject partial acceptance and record the worker/result observation separately. The Controller closes the validation boundary as `Fail` when the governed incomplete-result rule applies; retain expected/actual fields, pending channel data and cleanup outcome. |
| Worker hang / provider hang | Record `WorkerUnresponsive` where observed. The Controller closes the authoritative validation boundary at the finite governed deadline, fences all subsequent output, requests only approved cooperative cancellation, and records unresolved worker/provider state; no false `Disposed` outcome. |
| Late result / callback | Reject after cutoff, increment non-authoritative rejection evidence, prove authoritative state unchanged. |
| Stale generation or reused run identity | Reject before acceptance; retain generation mismatch/replay disposition without reopening prior terminal state. |
| Ownership mismatch, PID reuse, or stale/missing identity | `STOP — Ownership Revalidation Failed`; no process-affecting action or fallback. Retain full sanitized identity comparison and unresolved resource state. |
| Unexpected child, helper, conhost, or Job member | Fail closed on member set and role; no Job-wide cleanup or unknown-member termination; retain membership and provenance gap. |
| Disposal failure / unresponsive worker | Keep terminal result immutable but record `Disposal Failed / Isolated`; block GAP-B closure and new execution until separately governed resolution. Preserve every unresolved resource. |
| Audit-write or partial-write failure | Never report successful validation evidence; preserve primary outcome, sink failure, attempted reference and independent failure record without rewriting earlier artifacts. |
| Cleanup/`finally`, temporary-file or handle failure | Preserve exact disposal order, bounded wait, independent errors, final resource state and immutable authoritative-state comparison; no broader fallback authority. |

No unrelated process may be affected; no tenant/core/runtime state may be mutated; no global OS/CIM configuration or elevation is assumed. The worker executes only synthetic, read-only validation under separately approved source and scope. Unknown or unverified resources stay unresolved, not force-cleaned. The non-destructive safety rule applies equally to normal, timeout, exception, fallback, watchdog, and `finally` paths.

## 8. Disposal failure, direct evidence, and governance sequence

**`Authoritative result safely closed + worker disposal not proven` is a distinct auditable condition.** It preserves the one terminal authoritative decision and immutable cutoff, but cannot be counted as worker-disposal success or operational GAP-B closure. Retain run/generation, exact ownership comparison, target/member set, cancellation and timing, operation/session/handle state, attempted permitted cleanup, unresolved resources, sanitized failure category, and independent audit reference. Do not overwrite a failed attempt. A retry uses a new, separately governed run/generation; no unsafe fallback is authorized.

Newly authorized **direct** evidence, under a later approved boundary and reviewed exact source, must separately prove: finite authoritative closure; finite worker/isolation lifetime and deterministic non-destructive disposal on normal **and stalled-CIM** paths; independent full ownership and fresh pre-action verification; zero effect on unknown/unrelated processes; one immutable terminal state and cutoff; late/stale rejection; zero accepted post-closure mutation and closure/final state equality; disposal timing and both success/failure reporting; cleanup/`finally` ordering; and independently sealed, sanitized audit evidence. Existing retained smoke, diagnostic, fixture, and analysis results cannot be re-analyzed into this new proof. Formal OE-12 evidence still requires its separately authorized run and independent review.

Required sequence: **Separate Isolation-Boundary Design → Technical Governance Review → Exact-Byte Publication → Separate Owner Approval → Implementation Change-Control → Implementation Authorization → Exact-Source Implementation → Source Safety Review → Execution Authorization → Newly Authorized Direct Evidence → Independent Evidence Review → GAP Closure Decision**. No source work for the unresolved worker-disposal mechanism may begin before design review, exact-byte publication, and separate owner approval; no implementation may begin before implementation change-control and authorization. Before any later execution, identify the immutable reviewed source package and file/bundle SHA-256, prove `100% MATCH` of runnable bytes in a fresh execution location, reject unreviewed helpers, retain actual executable/launcher path, and independently accept the complete executable branch/API/ownership/cleanup map.
