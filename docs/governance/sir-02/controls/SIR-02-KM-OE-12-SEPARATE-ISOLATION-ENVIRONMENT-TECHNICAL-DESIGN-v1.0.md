## 3. Candidate boundaries compared

### Candidate V — one dedicated, run-bound Windows Hyper-V VM

**Exact conceptual boundary and owner (design inference):** one separately owned Windows guest VM per authorized synthetic run, with an outside-host authority retaining the immutable VM identity, creation record, host-side management capability, audit/failure sink and attempt ledger. Controller/Supervisor/Worker/helpers would be guest workload; host owner would permit only the reviewed image, exact source and run capability. VM guest OS/system processes are part of the isolation environment and cannot be silently assumed to be known OE-12 members. Host VM ID and `vmwp` are not a substitute for guest Node/conhost/helper tuples.

**Documented platform capability:** Hyper-V on Windows needs a qualifying Windows edition, SLAT/virtualization hardware and sufficient memory; the recorded configuration does not establish them ([Hyper-V system requirements](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/host-hardware-requirements)). `Stop-VM` requests guest shutdown; `-TurnOff` is an abrupt power-off with possible data loss ([Stop-VM](https://learn.microsoft.com/en-us/powershell/module/hyper-v/stop-vm?view=windowsserver2025-ps)). `Suspend-VM` pauses a VM, which can later be resumed ([Suspend-VM](https://learn.microsoft.com/en-us/powershell/module/hyper-v/suspend-vm?view=windowsserver2025-ps)). None of these references promises a 5 s completion bound, complete guest process identity, or non-effect on unknown guest members. Host management needs separately controlled Hyper-V authority; management documentation describes Administrator/Hyper-V Administrators requirements ([Hyper-V host management](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/manage/remotely-manage-hyper-v-hosts)).

| Path | Proposed owner, observed state, and failure gate |
| --- | --- |
| Creation/admission | Host owner would create and retain VM identity/image reference before guest starts. An independently trusted guest admission/identity path would have to register Controller, Supervisor, Worker, every helper and actual conhost with full tuples and retained handles, bind one run/generation and seal P1 receipts before ARM/CIM. **Direct R&D evidence required:** prove that host and guest observations together are complete and cannot be forged by Worker/guest caller. No such interface exists in the package. |
| Normal exit | Guest Worker/helper exit and stream EOF must be separately observed. Guest requests orderly close; host observes VM transition and retained handle/channel closure. Guest result cannot declare VM or every member disposed. |
| Real Worker hang / helper hang | Controller closes immutable result and fences late data within its bound; guest may request cooperative EOF/shutdown. `Stop-VM` may wait on the guest. `Suspend-VM` could stop guest execution as **an inference**, but also affects every guest process; it is not disposal, not shown finite, and is prohibited if any member is unidentified. `-TurnOff` is destructive and is **not** a permissible fallback for unresolved membership. The same rule applies when an identity helper itself hangs. |
| Controller failure / timeout / `finally` | A separate host authority would need to detect the failure, consume no second attempt, retain independent terminal/evidence-integrity status, reject late channels, and own VM/guest resources. Guest `finally`, stream close or host observer timeout cannot prove VM or helper exit. A host watchdog may observe and fence; it gains no unknown-member destructive authority. |
| Handles and deadlines | VM handle, guest process handles, guest CIM session, pipes, observer/helper, image and storage handles each need an owner and closure record. One monotonic run clock must start before first side effect; preserve the 8/10/2/2/500/5/45 s approved plan bounds and the unproven helper `≤5,000 ms` target. Neither Hyper-V command documentation nor retained source proves those deadlines across guest/host failure. |

**Prerequisites and change control:** supported host edition/build, Hyper-V feature/hardware/firmware availability, dedicated Windows guest image and license, host/guest accounts and ACLs, administrator or Hyper-V management authority, offline image/source transfer, trusted host/guest channel, guest PowerShell 5.1/Node/CIM capability, host evidence storage and any virtual switch/storage policy all require explicit inventory and separate approval before configuration or execution. No host eligibility or guest CIM behavior was probed. A VM may offer fuller Windows guest semantics than a container, but that is **design inference**, not verified compatibility or a safety conclusion.

### Candidate C — one run-bound Hyper-V-isolated Windows container

**Exact conceptual boundary and owner (design inference):** an independently governed Windows container host/runtime would own a unique Hyper-V-isolated compute-system ID and handle for one synthetic run. Controller/Supervisor/Worker/helpers would run inside its utility VM/container boundary; the external host authority would retain T1/E1/M1, creation and lifecycle evidence. The host-visible utility-VM process does not identify all Node/conhost/helper processes inside.

**Documented platform capability:** Hyper-V isolation places each Windows container in an optimized VM with its own kernel; host process listing does not reveal the container's workload process ([Windows container isolation modes](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/hyperv-container)). Windows client/container use requires a supported edition/build, Hyper-V and a container runtime; runtime installation is a new dependency/configuration step ([container requirements](https://learn.microsoft.com/en-us/virtualization/windowscontainers/deploy-containers/system-requirements), [container setup](https://learn.microsoft.com/en-us/virtualization/windowscontainers/quick-start/set-up-environment)). The HCS API documents clean shutdown, pause, forceful terminate and bounded *wait calls* for compute systems; a wait deadline alone does not cause safe disposal ([HCS API overview](https://learn.microsoft.com/en-us/virtualization/api/hcs/reference/apioverview), [HcsShutDownComputeSystem](https://learn.microsoft.com/en-us/virtualization/api/hcs/reference/hcsshutdowncomputesystem), [HcsPauseComputeSystem](https://learn.microsoft.com/en-us/virtualization/api/hcs/reference/hcspausecomputesystem), [HcsWaitForComputeSystemExit](https://learn.microsoft.com/en-us/virtualization/api/hcs/reference/hcswaitforcomputesystemexit)). `HcsTerminateComputeSystem` is forceful, so it cannot be a fallback while any member is unidentified ([HcsTerminateComputeSystem](https://learn.microsoft.com/en-us/virtualization/api/hcs/reference/hcsterminatecomputesystem)).

| Path | Proposed owner, observed state, and failure gate |
| --- | --- |
| Creation/admission | Runtime/HCS owner would create a unique compute system and retain its handle, image digest and run binding. A separate independently trusted inside/edge process inventory would have to prove each Node, PowerShell Worker, identity helper, actual conhost and host-managed member before provider influence. HCS system properties/process-handle APIs do not, by their mere presence, prove complete guest membership or P1 receipts. |
| Normal exit | Inside process exits and HCS compute-system exit require distinct observations; stdout EOF or container command exit cannot prove all helpers/providers gone. Host retains operation and process handles until exit/cleanup evidence is sealed. |
| Real Worker hang / helper hang | Cooperative signal and `HcsShutDownComputeSystem` may be attempted only with approved ownership. `HcsPauseComputeSystem` is a possible **design inference** for isolation but affects every process in the compute system, has no documented 5 s guarantee, and is not disposal. Forceful HCS termination is disallowed for unidentified members. A timed-out identity helper can remain live even when the client discards its pipes. |
| Controller failure / timeout / `finally` | Independent host owner would have to fence channels, preserve terminal/evidence-eligibility separation and observe compute-system state despite an inside Controller crash. HCS operation failure, host service failure or an unavailable host owner leaves disposition unproven. `HcsCloseComputeSystem` would release an owned handle, not prove a stopped compute system. |
| Handles and deadlines | Track compute-system/process/operation handles, runtime service, image/layer and mount handles, guest pipes, CIM session and observer. HCS asynchronous operation start is distinct from completed operation result. All seven plan bounds and helper `≤5,000 ms` need monotonic cross-boundary start/end/expiry records; no retained timing proof exists. |

**Prerequisites and change control:** supported Windows host edition/build and compatible Windows Server base image, enabled Hyper-V/Containers features, container runtime/service, image acquisition and provenance, host management account/ACL, HCS/API binding, storage/layer/network policy, guest PowerShell 5.1/Node availability and local CIM/`Win32_Process` provider behavior. The container's local CIM result may represent the container environment rather than the original Windows host; this is an **unverified semantic risk**, not an assertion that CIM is unsupported. Image, runtime and host version compatibility must be checked against the supported matrix ([Windows container version compatibility](https://learn.microsoft.com/en-us/virtualization/windowscontainers/deploy-containers/version-compatibility)). Any download/network, installation, feature enablement, service, privilege, OS policy or environment change requires separate change control. No such change occurred.

### Common timing contract for either candidate

These are proposed **measurement obligations**, not evidence that a VM or container meets them. A trusted outside observer must record monotonic start/end and UTC correlation, and fail candidate eligibility when an interval expires. A timer callback or successful API *start* is not the end event. The same deadline continues through exception and `finally`; it cannot be restarted there.

| Bound | Required start → end; expiry consequence |
| --- | --- |
| Worker startup `8,000 ms` | Trusted Worker creation/assignment event → independently verified READY **and complete member receipt**. Missing either at expiry withholds ARM; environment boot time is separately charged to the `45,000 ms` total, not silently excluded. |
| Provider observation `10,000 ms` | Authenticated ARM acceptance → validated candidate result or timeout-triggered closure. Expiry closes the authoritative state `Timeout` and fences later data; it does not prove guest/provider exit. |
| Authoritative closure `2,000 ms` | First trusted terminal trigger (result, timeout, failure or cancellation) → sealed terminal, Accepted Result Cutoff and state-at-closure reference. Evidence-write failure makes candidate ineligible without changing an already sealed terminal result. |
| Cooperative grace `2,000 ms` | Freshly authorized cancellation request → independently observed Worker/helper exit or grace expiry. Expiry escalates only to the separately approved non-destructive isolation path; none is currently identified. |
| Ownership freshness `500 ms` | Independent full-tuple/member observation timestamp → immediately following process/resource action; a stale observation blocks the action. Query duration alone is not observation age. |
| Disposal/safe isolation `5,000 ms` | First cancellation, exception, timeout or cleanup trigger needing disposition → independently observed exit **or qualifying safe isolation with all members accounted for**. `finally` cannot reset it. Expiry is D2 failure and cannot be relabeled PASS by cutoff or stream closure. |
| Total run `45,000 ms` | First execution-relevant side effect after T1 atomic claim, including image/source staging or environment creation if first → final terminal/evidence-eligibility and resource-disposition record. A hung event loop, guest or host observer cannot be excluded from this wall-clock bound. |
| Identity helper `≤5,000 ms` **unproven target** | Independently retained helper creation/assignment → observed helper exit or qualifying safe isolation, including its own query, pipes, handles and any console host. The owner selected this as a design target; operational use still needs separate execution authorization and direct evidence. It must fit inside, not extend, the applicable disposal and total deadlines. |

### Comparison and D2 criterion

| Dimension | Dedicated Hyper-V VM | Hyper-V-isolated Windows container |
| --- | --- | --- |
| Windows x64/PowerShell/Node fit | Full guest OS is a plausible host for the current script model; **guest installation and CIM behavior unverified**. | Windows user-mode workload plausible, but base-image/runtime and local CIM identity semantics **unverified**. |
| External isolation owner | Hyper-V host authority could retain VM ID/handle; owner, ACL and independent guest inventory not selected. | HCS/runtime authority could retain compute-system ID/handle; service/account and independent inner inventory not selected. |
| Host-visible actual membership | Host VM state is not a complete guest Node/conhost/helper list. | Hyper-V isolation hides guest workload processes from host process list; HCS compute-system identity alone is not the full member tuple. |
| Finite non-destructive response to real hangs | Cooperative guest shutdown may hang; pause is isolation but affects all guest members and has no demonstrated bound; turn-off is destructive. | Clean HCS shutdown may hang; pause affects all members and has no demonstrated bound; HCS termination is forceful. |
| Current decision | **Does not satisfy D2.** Potential subject for a new owner-scoped design only. | **Does not satisfy D2.** Greater runtime/image and guest CIM uncertainty. |

**Design conclusion: `Design STOP — no compliant boundary identified`.** Both are concrete Windows isolation environments with documented lifecycle controls, but neither retained source nor platform documentation supplies an independently authenticated complete Node/conhost/helper set **and** a measured finite safe-disposition path for a real hung Worker/helper that cannot affect an unidentified process. Pausing an environment is not disposal; forcibly stopping it affects all occupants. A host or utility-VM identity is not the ownership tuple. No candidate is preferred or selected for implementation. The relative full-guest compatibility of a VM does not overcome the D2 gate. Keep the published D2 STOP and return the unresolved choice/proof contract to the owner; do not substitute Option A or silently approve VM/container R&D.

## 5. Separate decisions required; preserved state

Before creating or configuring either environment, the owner would need a **new** scoped decision on the environment/host owner and exact isolation mechanism, membership and independent receipt method, handling of host-managed/system processes, permitted non-destructive isolation action, approved finite deadlines and expiry behavior, T1 verifier/key/ledger custody, E1 sink/ACL and M1 trust root/image/executable identity. A separately reviewed change-control package must enumerate edition/build/hardware, guest/image licensing and provenance, Hyper-V/Containers roles, runtime/service, account/privilege, storage/network, dependency and source/config impacts. If any requirement demands weakening OE-12 identity, finite disposal, late-result or no-unknown-process rules, stop for separate baseline change control rather than assuming an exception. No environment may be created from this design document.

Future sequence, only if the owner later commissions a credible exact mechanism: revised isolation-boundary design → independent technical review → exact-byte publication → separate owner approval → mechanism/dependency/environment change control → bounded source-change authorization → implementation → exact-source/path safety review and reviewed/runnable byte match → separate one-attempt R&D execution authorization → newly authorized direct evidence → independent evidence review → any GAP-closure decision. Until an exact safe mechanism is specified, **D2 Design STOP remains**.
