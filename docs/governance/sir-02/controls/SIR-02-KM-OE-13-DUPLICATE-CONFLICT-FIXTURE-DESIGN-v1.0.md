## Deterministic registry, duplicate, and conflict algorithm

1. Verify pinned input commit, path, SHA-256, accepted review, Gate A namespace/schema, synthetic tenant binding, and event chronology. Load accepted evidence read-only. Invalid or ambiguous evidence stops before submission and emits a safe failure, not a substituted fact.
2. Construct a clean in-memory registry and logical artifact inventory from the accepted lifecycle evidence. Record exact baseline keys, immutable citations, artifact identities and counts. Use canonical stable serialization, fixed sort order, and SHA-256 for reproducibility. No live knowledge artifact is materialized.
3. Process each isolated synthetic submission against exactly one `SourceVersionKey`; never search another tenant or canonical source as fallback. The test must distinguish registration identity from source/version identity. Check owner, checksum, approval, provenance, lineage, supersession, quarantine, and immutable refs against the authoritative record.
4. If a candidate is byte-equivalent in every governed field and immutable identity to the recorded registration/version, classify it `Exact Duplicate / No Op`. A second and subsequent repeat yield the same classification. Preserve the original record and provenance/audit chain; add **zero** active or downstream-processing artifacts and leave logical inventory counts unchanged. Emit a distinct sanitized no-op audit event. Do not treat a divergent field as an exact duplicate.
5. If identity is reused with divergent governed facts, classify every detected conflict by stable type and scoped synthetic key. Never choose the newer record, merge, overwrite, infer approval, or repair. A candidate carrying a different exact tenant or canonical source is distinct only when all bindings and authority are valid; an attempted foreign-tenant claim or substitution is denied without looking up or revealing protected foreign facts.
6. For each unresolved conflict, preserve the authoritative record and inventory unchanged, block source use, and append a **test-only** typed quarantine decision requiring a separate human lifecycle decision. A duplicate or conflicting quarantine decision is itself a conflict; do not produce competing authoritative quarantine states. Report the unique typed conflicts, per-type counts, total counts, and affected synthetic keys internally. The caller receives only a generic safe denial.
7. Record artifact counts before and after each submission, including active and processing-artifact counts. Exact repeat and every conflict must have zero additional active and processing artifacts; every conflict has zero downstream parsing/chunking, embedding, indexing, vector/storage-write, retrieval-preparation, and equivalent calls. A quarantine record is audit metadata and must not be counted as a knowledge-processing artifact.
8. For identical inputs, assert byte-stable canonical case output excluding separately recorded Gate A run metadata. Preserve original event timestamps separately from test execution time. Any unexpected exception, nonzero downstream call, duplicate artifact, missing quarantine decision, unsanitized output, or cleanup failure makes the case fail; no failure is reclassified as success.

## Required scenario matrix

Each case uses a fresh copy of the same accepted synthetic baseline. Independent test expectations must not be computed by calling the fixture's classifier. For combined rows, test each named conflict independently and retain one observation per subcase.

| Case group                                                       | Required input and observation                                                                                                                                                                                                                |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Clean baseline and exact repeats                                 | Load one immutable source registration/version; submit the exact record twice. Each repeat is a deterministic no-op with unchanged authoritative record, `0` extra active or processing artifacts, and traceable audit.                       |
| Duplicate source registration and duplicate exact source/version | Distinguish identical registration/version replay from reused registration or source/version identity with divergent facts; only the fully exact replay is suppressed.                                                                        |
| Divergent content and checksum                                   | Same key with changed content identity or checksum is typed, blocked, and quarantined; no overwrite.                                                                                                                                          |
| Approval and provenance                                          | Conflicting exact-version approval decisions/refs or origin/hop refs are typed, blocked, and quarantined; approval cannot be inferred.                                                                                                        |
| Lineage, supersession, stale/quarantine                          | Conflicting root/predecessor, supersession, and stale/quarantine refs or states are each typed, blocked, and quarantined without changing accepted chronology.                                                                                |
| Immutable references                                             | Duplicate/conflicting commit, missing/broken/mismatched immutable ref, and duplicate/conflicting artifact path are separately classified; invalid refs never become authority.                                                                |
| Tenant and source partition                                      | Same version across different valid tenants or canonical sources remains separately scoped; wrong-tenant submission and a cross-tenant injected duplicate/conflict are denied with zero protected-field disclosure and no cross-tenant merge. |
| Owner, chronology, authoritative ambiguity                       | Owner substitution, conflicting event order, competing authoritative states, wildcard source/version/tenant/owner, and duplicate/conflicting quarantine decisions each fail closed with typed outcomes.                                       |

The complete case inventory must cover all 20 requested categories and their independent subcases, with explicit expected conflict type and count for each. Exact duplicates are no-op outcomes; unresolved divergent conflicts are quarantined. A valid same-version record in another tenant or canonical source is not itself a conflict. No case may mark an unapproved successor approved or restore superseded/quarantined content to active use.

Use stable internal classifications: `EXACT_DUPLICATE_NO_OP`, `REGISTRATION_ID_CONFLICT`, `SOURCE_VERSION_CONFLICT`, `CONTENT_IDENTITY_CONFLICT`, `APPROVAL_CONFLICT`, `PROVENANCE_CONFLICT`, `LINEAGE_CONFLICT`, `SUPERSESSION_CONFLICT`, `STALE_QUARANTINE_CONFLICT`, `IMMUTABLE_COMMIT_CONFLICT`, `ARTIFACT_REFERENCE_CONFLICT`, `TENANT_BINDING_CONFLICT`, `CROSS_TENANT_INJECTION`, `OWNER_CONFLICT`, `CHRONOLOGY_CONFLICT`, `AMBIGUOUS_AUTHORITATIVE_STATE`, `WILDCARD_IDENTIFIER`, and `QUARANTINE_DECISION_CONFLICT`. A valid same-version record in another tenant or canonical source receives `DISTINCT_SCOPED_IDENTITY`, not a conflict. Duplicate exact source/version uses `EXACT_DUPLICATE_NO_OP` only when all governed fields and immutable identity agree; otherwise it uses the specific divergent code(s). Emit each code once per affected key and conflicting reference pair, sort codes and keys, and count actual occurrences without inflating counts for repeated validation of the same pair. The integration test must assert these codes and numeric counts independently of the classifier.

## Observable output and safety contracts

**Per-case internal result:** case ID; input and baseline immutable reference IDs; original lifecycle event timestamps; synthetic scoped identifiers; candidate/authoritative record hashes; classification; typed conflicts and exact per-type/total counts; registry state hash before/after; artifact inventory hash and exact active/processing counts before/after; quarantine decision (or explicit absence for exact no-op); measured downstream counters; disclosure count; audit ID; cleanup status; expected/observed/pass status.

**Caller-visible result:** fixed no-op or generic blocked decision with opaque sanitized correlation ID. A blocked Tenant B caller receives no Tenant A source ID, title, owner, version, checksum, approval, provenance, lineage, artifact path, conflict detail, or existence signal. Protected-field disclosure measurement must equal `0`.

**Audit output:** UTC event time, test-only event type, synthetic scoped actor/tenant, request/correlation/trace IDs, outcome, stable conflict codes and counts, immutable reference IDs safe for the scope, before/after logical artifact counts, no-op or quarantine reference, and downstream counter snapshot. Exclude raw content, real tenant data, secrets, untrusted assertion payloads, and foreign-tenant protected fields. An audit emission failure fails the case.

**Future formal OE-13 evidence artifact:** a versioned JSON file under `docs/governance/sir-02/operational-evidence/oe-13/` containing Gate A deterministic run ID, UTC execution time, executor/reviewer, implementation and independent implementation-review commits, namespace/schema/classification, pinned accepted-input manifest, clean and every scenario/subcase result, registry/artifact hashes and exact counts, quarantine decisions, zero-call and disclosure measurements, sanitized audit, cleanup and live-operation counters, overall execution result, and `acceptance_status: Not Reviewed`. SHA-256 is calculated over the completed file and linked to an immutable evidence commit; no self-referential checksum is embedded. A later independent review alone may accept OE-13.

## Cleanup, validation, and authorization hold

Every case starts with a new registry, logical artifact inventory, quarantine/conflict buffer, spy counters, and synthetic request context. A fail-safe `try/finally` or equivalent clears/discards all of them after normal success, denial, early return, assertion failure, or adapter exception. Tests must prove no counter, tenant identity, registry entry, inventory entry, or quarantine decision leaks between cases. Cleanup failure is reported separately without hiding the primary failure. Only a future immutable governance evidence artifact may persist; no live state or processing artifact may remain.

After separate owner authorization, implementation validation must include the complete OE-13 test suite, relevant repository regression tests, lint, typecheck, formatting, exact two-file change check, accepted OE-09/OE-11 byte integrity, deterministic replay, exceptional cleanup, and zero live-operation counters. Any need for another file, adapter, dependency, migration, or runtime change requires a revised design and owner decision before coding.
