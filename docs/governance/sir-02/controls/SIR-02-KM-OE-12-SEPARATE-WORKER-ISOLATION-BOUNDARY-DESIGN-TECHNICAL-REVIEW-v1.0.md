## 3. Exact clarification required

The active [OE-12 Criterion Amendment v1.1](SIR-02-KM-OE-12-CRITERION-AMENDMENT-v1.1.md) defines authoritative terminal states as **`Success`, `Fail`, `Timeout`, `Cancelled`**. The [Authoritative Validation-Boundary Detailed Design v1.0](SIR-02-KM-OE-12-AUTHORITATIVE-VALIDATION-BOUNDARY-DETAILED-DESIGN-v1.0.md) uses the same authoritative vocabulary. The draft under review says `Succeeded`, `Failed`, and `TimedOut` in its *worker lifecycle* (section 5), which can be valid as separate worker-status names. Its section 7, however, says “close once as `Succeeded`,” “close as `TimedOut`,” and “close as `Failed`” in the normal, timeout, worker-exception, provider-exception and partial-result rows. The object of **close** is not identified there. Section 3 separately says the immutable authoritative state has `Success/Fail/Timeout/Cancelled`, creating an exact-byte inconsistency in the executable-path contract.

Minimum correction for a later, separately authorized draft edit: identify the worker outcome and authoritative terminal outcome explicitly for each affected row; use only the baseline-authorized authoritative terminal names when describing validation-boundary closure. Preserve the `Design STOP`, disposal object, ownership, safety and governance findings. The current design must remain unchanged during this review, and any corrected bytes require a new SHA-256 and exact-byte technical re-review. This finding does not authorize a mechanism, criterion change, implementation or execution.
