## 2. R2 — trusted outer entry and one-use attempt transition

**Current first reachable source:** a caller can start `RD/controller.mjs` directly in Node, `RD/supervisor.mjs` directly in Node, or `RD/worker.ps1` / `RD/identity.ps1` directly in PowerShell. Node evaluates static imports before calling `controller.mjs:main()` or `supervisor.mjs:main()` and before `guard.mjs:executionGate()`. The currently imported `guard.mjs` and `protocol.mjs` have no observed process/file-write side effects at top level, but a later import cannot be assumed inert. On the ordinary current Controller path, after `executionGate()` reads/compares caller-supplied inputs, the first state-changing I/O is `controller.mjs:55` `openSync(auditPath,'wx')`; then `controller.mjs:74` spawns Supervisor, which can reach `supervisor.mjs:66` worker `spawn`. A directly invoked Supervisor can reach worker creation without Controller's audit open if its self-supplied gate is made to pass. A directly invoked Worker/Helper can reach READY/CIM under the self-supplied authorization/hash boundary described in the rejected preflight. None of these paths contains a trusted attempt-consumption operation.

**Proposed future entry contract:** a separately approved trusted outer entry must be the *only* authorization-to-execution route. It may perform read-only inspection of immutable decision, exact manifest, source/config bytes, environment and executable paths before claiming an attempt. It must then make an **independently anchored, atomic, durable, replay-resistant transition** `Available → Consumed` for exactly one authorization/run/generation/case/package/evidence destination. The successful consumed-attempt receipt must be bound to the approved decision and inaccessible for minting or resetting by the caller, Controller, Supervisor, Worker or Helper. It is a one-use precondition, not a caller-supplied JSON/hash/nonce. Only after the transition is durably acknowledged may the outer entry dynamically import candidate JavaScript, create an audit file, spawn Supervisor/Worker/Helper, send ARM or perform CIM. Thus in the **proposed approved path** the attempt-ledger transition is the first execution-relevant state-changing operation; candidate import, `openSync`, and process creation are later. Failed claim means no candidate import or process launch; any failure/crash after claim leaves the attempt **Consumed / Failed or Unresolved**, never reusable, and a retry requires separate authority. An independent record must retain claim identity/time/result even if Controller audit creation fails.

**Direct-entry contract:** future `controller.mjs`, `supervisor.mjs`, `worker.ps1`, and `identity.ps1` must fail closed without independently verifiable consumed-attempt capability bound to that exact role and run. Node static imports must be side-effect-free and source-reviewed; any side-effecting candidate import must move behind the outer verified/consumed gate. A direct invocation may parse inputs and perform read-only checks, but must not create evidence, spawn, emit READY, query CIM or otherwise influence a worker before trusted verification. The Worker and Helper must verify authority through an independent channel/anchor, never a caller-supplied record plus its caller-supplied hash. `RD/guard.mjs:executionGate()` lines 17–56, `RD/controller.mjs:main()` lines 50–75, `RD/supervisor.mjs:main()` lines 49–74, `RD/worker.ps1` lines 16–55, and `RD/identity.ps1` lines 17–40 require new exact branch maps. The chosen trust root, outer entry and atomic ledger are **owner decisions**, not selected by this document.

## 4. R5 — atomic validation and authoritative result commit

The current `RD/supervisor.mjs:94–105` can emit `MalformedWorkerOutput` without a corresponding Controller failure branch, while `RD/protocol.mjs:AuthorityFence.receive()` lines 31–41 updates `lastSequence` and `accepted` for a valid tag/sequence even when `payload` is null; `RD/controller.mjs:109–114` can then select Success on code 0 plus any accepted frame. The future source must separate **non-authoritative receipt/quarantine** from **authoritative commit**:

1. Parse and validate the complete versioned frame, payload fields/types/cardinality, provider status, run/generation, sequence, query/identity binding and evidence eligibility in a non-authoritative buffer. Malformed, partial, null, duplicate, stale, late or provider-failure input is rejected there. Before and after that rejection, the authoritative snapshot is byte-identical: `lastSequence`, accepted set/count, terminal eligibility, cutoff, terminal state and state hash have **zero mutation**. Rejection count/details belong only to separately identified non-authoritative audit metadata.
2. Only a completely valid, in-window frame with durable acceptance evidence may enter one Controller-owned `commitValidResult` transition. That operation is the single boundary at which sequence and accepted set/count can change. Re-review must map its exact source line/API and failure before/after the commit. `Success` additionally requires full validated result and complete evidence; worker exit code alone cannot establish it.
3. A malformed frame may cause a **separate governed Controller channel-fault decision** to close the boundary as Fail; that independent terminal transition must be recorded as such and must not incorporate malformed payload or be mislabeled as a frame acceptance. If rejection audit fails, candidate evidence integrity fails under R7; no authoritative payload mutation is permitted.

WH-01/04/05/06/10 negative variants must inject null, missing mandatory field, partial JSON, malformed JSON, provider exception, duplicate/replay, wrong generation and late frame. Evidence must compare authoritative snapshot/hash before and after rejection, show zero accepted partials, retain rejection disposition separately, and show closure/final equality after the governed terminal event.

## 5. R6 — numeric identity-helper lifetime and existing bounds

The approved plan contains startup `8,000 ms`, provider observation `10,000 ms`, authoritative closure `2,000 ms`, cancellation grace `2,000 ms`, ownership freshness `500 ms`, worker disposal/safe isolation `5,000 ms`, and total run `45,000 ms`. These remain proposed, unproven R&D limits. The `500 ms` value measures **age of a completed identity observation at the action**, not helper query duration or helper lifetime. Current `RD/supervisor.mjs:observeIdentity()` lines 12–35 may use 8,000 or 500 ms as a race timeout; `RD/controller.mjs:independentIdentity()` lines 15–39 uses 500 ms. Both can `unref` a timed-out helper and destroy pipes without observing exit.

**Proposed numeric helper ceiling, pending owner decision:** `T_helper_end_to_end ≤ 5,000 ms`, measured by one monotonic clock from **before `spawn(identity.ps1)`** until observed helper exit with all owned handles closed, or an independently approved qualifying non-destructive isolation state with retained handle/session and no authoritative late-result path. This 5,000 ms candidate is chosen as a conservative ceiling equal to the existing disposal/safe-isolation bound, not as an already approved interpretation of that worker bound. The owner must approve or replace this value and its applicability before any helper source work or runtime test. No defensible helper-specific value is already approved; until decision, readiness remains STOP.

The helper deadline is `min(helper_start + owner-approved T_helper, run_start + 45,000 ms, active_disposal_start + 5,000 ms if disposal has begun)`. It never resets in catch/finally. Startup must still finish through authenticated READY within 8,000 ms; a helper budget cannot extend that window. Provider 10,000 ms and closure 2,000 ms are separate authority clocks and cannot be used to imply helper exit. On helper deadline expiry, record `HelperUnresolved / Disposal Not Proven`, reject its result, withhold ARM/cleanup action requiring that identity, close or invalidate the candidate under governed rules, and retain all live handle/session/member evidence. `unref()` or pipe destroy is not exit/isolation proof; no destructive unknown-member fallback is allowed. If qualifying isolation cannot be established within the approved bound, the case fails and R&D execution remains blocked until a separate boundary decision. Future WH-01/02/04/07/08/10 and an explicit helper-hang negative case must retain helper creation time, timeout, cooperative signal, observed exit/isolation time, owner-approved limit, global/disposal remaining budgets and expiry disposition.

## 6. R7 — immutable terminal result versus candidate evidence eligibility

The current `RD/controller.mjs:audit()` lines 55–58 and catch/finally/sidecar lines 123–140 can fail after `RD/protocol.mjs:AuthorityFence.close()` lines 43–53 has fixed a terminal state. The future source must maintain **two distinct domains**:

- **Authoritative validation state:** exactly one immutable `Success | Timeout | Fail | Cancelled`, Accepted Result Cutoff, accepted set and closure hash. Once terminal, it cannot be rewritten because an audit or sidecar later failed; late results cannot change it.
- **Candidate eligibility / evidence integrity state:** initially `Pending Evidence`; it becomes `Evidence Complete / Eligible for Independent Review` only after all mandatory audit, sidecar, closure/final hash and resource evidence is durably retained and independently verified. Any mandatory `openSync`, `writeSync`, sidecar, flush or final-evidence failure, including **after a terminal Success**, irrevocably sets `Evidence Incomplete / Candidate Cannot Pass` for that attempt. This is a separate candidate disposition, not a mutation of the terminal result. No retry or rewrite under the consumed attempt is permitted.

A trusted, independently anchored failure sink must retain the error/API, phase, terminal snapshot if already fixed, candidate disposition, exact evidence gap and unresolved resource state. If that sink itself is unavailable, record/retain an explicit unresolved STOP through the approved outer authority; never infer PASS from silence. The sink, evidence destination/schema and retention authority require an **owner decision**. WH-01/02/04/09/10 negative evidence must cover denied create, partial write, full disk, sidecar failure and post-terminal/finally failure; show terminal immutability, candidate invalidity and independent failure retention. No audit-failure branch may call the same failed writer as its only fallback.

Future WH-01–WH-10 negative tests must change one byte, executable resolution, config, manifest, evidence input, helper or authorization reference and retain an independent mismatch verdict with zero candidate import/spawn/CIM side effects.
