## 1. Boundary purpose and limits

The owner approved detailed-design **preparation**, not a concrete controller, receipt producer, worker, process model, storage technology, source modification, or execution. This design describes the proof obligations for the candidate **Authoritative Validation-Boundary Quiescence** criterion. It does not demonstrate that the required bounded lifetime is implementable under the present host and non-destructive cleanup boundary.

Conceptual flow: **independent receipt/trust boundary → validation run/generation controller → read-only CIM validation worker/boundary → authoritative result state → late-result fence → independent audit evidence**. The result state and fence are separate logical responsibilities even if a later approved design places them together. No one component may self-assert process creation, ownership, validation, **and** acceptance without an independently anchored trust boundary. In particular, a worker/probe cannot issue its own ownership receipt and integrity hash through the same controlled input, and it cannot directly commit an authoritative result.

Validation-boundary quiescence means the authoritative OE-12 validation outcome is closed, immutable, and insulated from all later provider activity/result deliveries. It **does not claim provider-level physical quiescence** of a shared CIM provider. The proposed criterion would explicitly change the active safety contract only after separate versioned baseline approval.

## 2. Mandatory GAP-A dependency

**GAP-A — Independent Receipt Trust Boundary = OPEN.** A future producer must be independent of the CIM probe, create the receipt before validation, and anchor integrity outside probe-controlled input. The receipt must bind the exact synthetic run token to `PID + image path + parent PID + creation time + run token + creation/assignment event`, plus process handle/session/Job evidence where applicable. The design must prove producer identity, pre-probe creation, immutable run binding, PID-reuse resistance, and fresh full-identity and membership revalidation immediately before any process-affecting action. A PID list, matching self-reported fields, or a probe-supplied receipt/hash is insufficient. No producer, anchor mechanism, or ownership proof is fabricated or selected here. Until separately designed, reviewed, and authorized, this remains a mandatory blocker to execution.

## 4. Terminal state, cutoff, and race control

Only `Success`, `Fail`, `Timeout`, or `Cancelled` may be the terminal validation state. The controller must select exactly one terminal state and reason within the approved bound. Boundary closure and the **Accepted Result Cutoff** must form one ordered decision against result acceptance. While the boundary is open, a result is accepted only if its run/generation matches and its trusted validation conditions pass. At closure, the explicit cutoff fixes the last accepted ordering marker and sealed accepted set; every later marker or delivery is rejected. If closure races an arrival, the later detailed design must prove a single order: either the result is included in the sealed accepted set before closure, or it is `Late / Rejected` afterward. There is no third or ambiguous outcome.

At closure, retain run ID, generation ID, closure timestamp, immutable cutoff, final accepted count, terminal state/reason, and authoritative state version/hash or equivalent immutable reference. After terminal closure: no return to active; no cutoff movement; no run/generation reuse; no alteration of accepted set, terminal reason, ownership state, or authoritative audit decision. Reopening requires a separately governed new run/generation, not mutation of the old one.

For every observed late/stale result or callback: verify run/generation, verify open/closed state and cutoff, then reject after closure or on mismatch. Retain late-result count and per-result sanitized rejection disposition where applicable. After all observed late handling and disposal, retain final authoritative state version/hash, accepted post-closure mutation count `0`, and the comparison `authoritative_state_after_closure == authoritative_state_at_closure`. Separately labeled **non-authoritative audit metadata** may record rejection without changing the authoritative result. The cutoff cannot be reconstructed later from logs.

## 5. Future executable path contract

The following table states required behavior, **not actual source branches or API calls**. Before any execution, independently reviewed exact source must map every applicable path as `trigger → exact reviewed source → branch/function → exact API/call → state transition → ownership check → cleanup/disposal → retained evidence`. Record `Ownership Check = Required` or `Ownership Check = Not Applicable — <reason>` for each path. Where a path can affect a process/resource identity, `Required` means fresh revalidation immediately before that action of `PID + image path + parent PID + creation time + run token + creation/assignment evidence`, plus handle/session/Job evidence where applicable. Missing/mismatched/stale identity, PID reuse, or unexpected membership is `STOP — Ownership Revalidation Failed`; no primary or fallback path may bypass this gate. A non-process path must state why ownership checking is inapplicable. A comment or prose description cannot satisfy the future executable source gate.

| Trigger/path | Required conceptual state result | Cleanup and retained evidence obligation |
| --- | --- | --- |
| Success | Accept only fully validated pre-cutoff result; close once as `Success`. | Prove bounded worker/isolation completion, closure hash/cutoff, deterministic disposal, and independent audit. |
| Inner timeout / outer watchdog timeout | Close within approved bound as `Timeout`; reject any later result. | Record both timeout stages, outstanding operation state, cooperative signal, bounded observation, disposal result, and unresolved resources without treating timeout detection as provider completion. |
| Exception / launcher exception | Close as `Fail` if a run is active, or record a pre-run failure without creating a false terminal run. | Sanitize exception, release owned handles/resources deterministically, retain branch, cleanup, and audit outcome. |
| Cancellation | Close once as `Cancelled`; later completion cannot change status. | Record request/acknowledgment, bounded wait, unresolved operation state, disposal, and terminal evidence. |
| Partial result / missing mandatory field | Never promote incomplete data to authoritative success; close `Fail` when required. | Retain bounded sanitized missing-field category, accepted-set cutoff, and cleanup. |
| CIM provider/service failure | Close `Fail` with tenant-safe sanitized category. | Record provider status/error when available, operation/session state, and disposal; do not infer quiescence. |
| Late result or callback | `Late / Rejected`; authoritative terminal state and accepted set unchanged. | Retain run/generation, cutoff, rejection reason/count, and closure/final state comparison. |
| Stale generation / PID identity mismatch | Reject; never let a prior generation or reused PID satisfy current trust/acceptance. | Retain sanitized mismatch, independent receipt reference, fresh identity result, and safe cleanup status. |
| Cleanup / `finally` / evidence-write failure | No fallback may enlarge authority or report success after missing closure evidence. | Record final state/hash comparison, handle/resource disposal order and outcome, temporary-file cleanup, audit sink/partial-write failure, and any unresolved resource. |

The watchdog may observe, signal cooperative cancellation, and capture evidence only. It cannot silently terminate an unknown process, close a Job handle as a destructive test with unresolved membership, call `TerminateJobObject`, `TerminateProcess`, `Stop-Process`, or `taskkill`, or bypass ownership gates. A future mechanism requiring destructive action, privilege elevation, Windows/CIM configuration, new dependency, or production/runtime change must stop for separate change control. No cleanup or fallback path may have broader authority than the primary path. A bounded validation decision must not be misreported as a proven bounded worker disposal if the latter is unresolved.

## 6. Source integrity, audit, and baseline impacts

Any later implementation proposal must identify exact source files and immutable commits, hash every reviewed source/bundle, copy runnable material to a fresh execution location, require a `100%` byte/hash match, reject unreviewed helpers, and retain the actual executable/launcher path. Source-level review must accept the executable path map above before separate owner execution authorization. This design cannot satisfy that gate by itself.

Independent audit must retain run/generation, trusted synthetic tenant/request/correlation/trace, independent receipt reference, closure timestamp, terminal state/reason, explicit cutoff, accepted count, closure and final authoritative state references, late rejection evidence, zero accepted post-closure mutations, cleanup outcome, sanitized failure categories, and immutable source/evidence references. The worker cannot self-authorize its result or rewrite these authority records. Existing OE-12 lifecycle audit, tenant-safe denial, sanitization, sink-failure, and OE-08 synthetic audit-only controls remain in force.

## 7. Open proof obligations and approval boundary

No independent receipt producer/anchor is selected or proven (**GAP-A OPEN**). No concrete non-destructive mechanism has yet proven the finite worker/isolation lifetime and deterministic disposal for an unresponsive CIM operation. These are design and source-review gates, **not assertions of feasibility or operational GAP-B closure**. The Alignment GAP remains **OPEN**. For both GAP-A and GAP-B, **`GAP Closure = Approved Applicable Design/Boundary AND Newly Authorized Direct Evidence`** demonstrating the applicable acceptance criteria. Design approval alone, evidence against an unapproved boundary, re-analysis of the same retained evidence, or inference from adjacent controls cannot close either GAP.

No STOP condition was encountered merely to prepare this conceptual proposal. **STOP before source implementation** if a concrete design requires production/runtime modification, tenant/security weakening, criterion change beyond the approved direction, elevation, Windows/CIM configuration, a new dependency, or destructive cleanup. Record and separately govern that requirement; do not work around it. These five proposal documents do not activate the new criterion, supersede the current baseline, authorize code or execution, or permit Diagnostic v4, launcher v1.4, Smoke v5, or formal retry `0003`.
