## Intake and failure behavior

`tests/evaluation/support/findings-registry.ts` defines the strict version 1.0.0 schema.
The fixed `registry.v1.json` path is mandatory for `evaluate:phase10`, including when run
through `validate`. Missing/unreadable input, malformed or duplicate JSON keys (including
escaped aliases), unknown fields/enums, duplicate IDs, broken internal references,
contradictory states, unknown severity, incomplete inventory or unreviewed findings fail
integrity. Every source and evidence reference must be a nonempty HTTPS URL; internal IDs
must resolve within the declared source inventory. URL syntax and candidate digests are
not evidence validation. Actual source content and reference resolution remain obligations
of an independent authority. An unreachable or misleading URL cannot become trusted here.

Registry ID/revision, repository, phase and evaluated Git HEAD commit are bound in every
authorization request, together with the SHA256 of the exact input bytes and the complete
parsed registry. Each finding has a stable ID, revision, severity, state, source/evidence
references, remediation references and separate verification references. Revisions must
advance under the future authority's independently maintained current-state policy; this
stateless reader does not create that policy or certify a dirty working tree as a release.

`unreviewed`, `open`, `remediation_claimed` and `verification_pending` remain unresolved.
Only independently authorized `verified_closed` findings map to resolved. Closure requires
remediation and separate verification evidence. Existing unresolved High/Critical policy,
runtime safety gates and quality thresholds are unchanged. Integrity diagnostics are separate
from actual classified findings: no synthetic finding or fabricated severity is inserted.
Only known-severity records enter the legacy projection, and every projected record remains
unresolved when integrity fails. Unknown records remain in the registry and diagnostics.
The CLI's `blocking_findings` contains only actual unresolved High/Critical policy findings.
Overall evaluation fails if registry integrity fails OR the existing runtime gate fails,
even when the projection and `blocking_findings` are empty. The CLI emits separate
`findings_integrity` diagnostics and `governance_status: BLOCKED` for integrity failure,
and exits nonzero even when runtime safety and quality evidence passes.

## Activation limitation

A checked-in `evaluated_commit` cannot contain its own enclosing commit SHA. In addition,
Git HEAD does not identify dirty working-tree contents. The current scope check therefore
cannot establish exact release-artifact authorization. Future activation requires a separately
reviewed detached attestation or exact artifact binding under independent authority.
Accepting HEAD's parent or a candidate-selected commit is not an allowed workaround.
This limitation is documented, not repaired or bypassed by this bootstrap.
